### 2.1 `in_stack` still fires on a function's own locals

The previous pass fixed the interleaved-prologue case. It did not fix the case
where the prologue is not in the entry block at all:

```
__aeabi_uldivmod  FUN_0000e244   frame 0   in_stack [4, 8, 12]   -> "arity 8"
```

`frame 0` means the entry-block scan found no `push`/`sub sp`, so every
`[sp,#N]` read after the *later* push looks like an incoming stack argument.
Believing it gave `__aeabi_uldivmod` **arity 8** and `__aeabi_ldivmod` the same.
**Rule adopted: `in_stack` is trusted only when `frame > 0` and the slots start
at offset 0.** `gui_utf_draw_align_right` (frame 768, slots from 0) survives the
rule; the two `__aeabi_*` helpers do not.

### 2.2 A self-clearing idiom counts as an argument read

```
assert_post_action  FUN_0007e2ec
  0007e2ec  eors r0, r0        <- reads r0; the value cannot be observed
  0007e2ee  msr  basepri, r0
  0007e2f2  mov.w r0, #4
  0007e2f6  svc  #2
  0007e2f8  bx   lr
```

`eors r0,r0` is a *read* of r0, so `in_regs=[0]` and the oracle called the #3
highest-yield symbol in the corpus "arity ≥ 1". It is arity 0 — and its
`ret_r0_expl=True` is the SVC number, not a return value. Swept for the pattern
(`eor/sub/mov/bic rX,rX[,rX]` before any other write of rX): **3 functions in
2,377** — `FUN_0004ff00`, `FUN_0004ff38`, `FUN_0007e2ec`. Narrow, but it hit a
symbol worth 23 translation units.

### 2.3 A tail-call thunk hides its pass-through arguments

```
log_msg_create_3arg  FUN_00082a42:  movs r3,#0 ; b.w z_log_msg_runtime_create
bt_log_forward_3arg  FUN_00080ea2:  movs r3,#0 ; b.w z_log_msg_runtime_create
smp_log_message      FUN_00083074:  movs r3,#0 ; b.w z_log_msg_runtime_create
```

None of the three *reads* r0–r3, so `in_regs=[]` and the oracle says arity 0 —
yet all three pass r0, r1, r2 straight through and only supply r3 themselves.
`scratchpad/td2/thunks.py` finds **94 such thunks** in the app image and gives
each the target's argument registers minus the ones the thunk writes: arity
**3** for all three above, which is exactly what their majority declaration
says.

### 2.4 `ret_r1_expl` is NOT evidence of a 64-bit return

```
z_spin_unlock_valid  FUN_0007205c
  0007205c ldr r2,[pc,#0x14] ; 0007205e mov r3,r0
  00072060 ldrb r1,[r2,#0x10]           <- r1 written on every path ...
  00072066 ldr  r1,[r0]                 <- ... as pure scratch
  00072068 movs r0,#0 ; ... ; bx lr
```

`ret_r1_expl` is True and r1 is scratch. An earlier version of this pass's
canonicaliser used `ret_r1_expl` to *force* a 64-bit return and produced
`extern uint64_t z_spin_unlock_valid(uint32_t);` — an ABI change in the growing
direction, the mirror image of the `__floatdidf` narrowing the previous pass
caught by hand. **Rule adopted: only the parity-proven DEFINITION may assert
64-bitness; the image can only REFUTE it, via `ret_r1` (r1 not live at the
return at all).** Under that rule `memset_bytes`, `memcpy` and
`assert_post_action` are provably 32-bit-or-void (their `ret_r1` is False) while
`get_dashboard_sum_time` and the `__aeabi_*` helpers are refused.

## 3. Round 1 — canonicalise the declarations, gate on per-object byte identity

### 3.1 The gate this pass uses, and why it is stronger than "Δ`.text` = 0"

Renode belongs to another agent this pass, so no framebuffer and no sensor
stream can be re-captured. The previous pass's Pass 1b showed **+60 B of
`.text` reorders two firmware threads on a shared I²C bus**; iteration 42 showed
+16 B collapses the dashboard. With no behavioural oracle available the only
honest standard is one that makes the behavioural question *vacuous*:

> **every retained edit must produce a byte-identical object file.**

If every object is byte-identical and the link order is unchanged, the linked
image is byte-identical, and every behavioural measurement already captured
carries over by construction rather than by argument. Files that fail the gate
are reverted, not rationalised.

### 3.2 How the canonical prototype is chosen

`scratchpad/td2/canon3.py`, per symbol:

1. the image gives corrected arity, whether a value comes back, and whether r1
   is a return half (§2);
2. candidate spellings are every spelling that already exists in
   `recon/symbolized/app` — **nothing is invented**;
3. spellings contradicting the image are struck out (wrong arity, variadic when
   the body has no save area, 64-bit when r1 is not live);
4. of the survivors, the arity the parity-proven definition declares is
   preferred (majority vote alone gave `bt_conn_create_pdu` six parameters where
   the image proves five);
5. the winner is rendered in **base C only** — `uint32_t` → `unsigned long`,
   `uintptr_t`/`size_t` → `unsigned int`, which Stage 04 §3.0.1 measured to be
   the *same type* on this target — so it cannot drag a typedef into a file that
   does not declare one. A canonical that still needs a project typedef (`u32`,
   `uint`, `byte`) or a struct tag is **refused**;
6. a file is skipped when its own call sites do not fit the canonical (wrong
   argument count, or the result is consumed and the canonical is `void`).

`__`-prefixed compiler-runtime helpers are excluded outright: their prototypes
are ABI-fixed and majority vote gets them wrong.

## 4. Rounds 2 and 3 — the frozen-spelling rule

A file that failed either gate in round 1 **freezes** its symbol's spelling: no
matter what the rest of the corpus is canonicalised onto, that file will still
disagree, so the canonical is chosen to be *the frozen file's spelling* whenever
that spelling survives the image filter. Round 2 also widened the target set

### 4.1 A methodology defect in my own loop, found and corrected

Rounds 1–3 gated against an **incremental** build directory. When I restored the
tree from a `cp -a` backup between the discarded first plan and plan 2, the
restored files got their *original* mtimes — older than the objects ninja had
already built from the discarded plan — so ninja considered them up to date and
never recompiled them. `gpio_pin_check_output_available.c.obj` differed for
three rounds with a source byte-identical to the baseline, and the difference
was real codegen (`and.w r0,r3,#1` vs a `cbz`) left over from the *discarded*
plan.

That makes every incremental measurement above advisory. **The authoritative
numbers in §5 come from a from-scratch clean build**, and under it
`gpio_pin_check_output_available.c.obj` is byte-identical, confirming it was a
stale object and not a regression.

## 9. What I did NOT close, and why

1. **677 of 833 entries remain open.** 365 are ABI-real disagreements this pass
   did not settle; 168 are false alarms that still need canonicalising for the
   merge but cannot be canonicalised without moving bytes; 144 are
   confirmed-real defects with per-site image evidence and no repair.

2. **The 156 fixes are entirely in the DECLARATIONS. Not one call site was
   changed and not one function body was changed.** That is a deliberate scope
   limit, not an oversight: every call-site repair either invents a value or
   emits an instruction, and this pass's entire standard is byte-identity.

3. **366 image-proven missing-argument call sites are untouched** (§7.1). The
   previous pass repaired the 53 that were free — where the value was already
   in the register as the enclosing function's own incoming argument. The
   remainder need a value *reconstructed*, which is a `cfg_verify` re-proof per
   enclosing function and a `.text` move, and the emulator to confirm it. **A
   wrong argument is worse than a missing one.**

4. **The 2 surviving short definitions are identified, not repaired**
   (`z_impl_k_timer_start` 3 vs 6, `main_dispatch_thread_tick` 7 vs 8). Adding a
   parameter changes the body's contract and needs a per-function re-proof plus
   a matching repair at every call site.

5. **The 303 invented-argument sites were not touched.** The previous pass's R8
   triage (287 inert / 21 volatile / 0 call) stands; deleting ~287 argument
   setups moves `.text` in the shrinking direction by far more than the 60 B
   that already broke a gate, and there is no oracle available this pass to
   check it. Explicitly deferred to a pass that owns Renode.

6. **The `u8` typedef collision in `__ieee754_exp.c` is NOT fixed.** It is still
   the highest-risk unclosed item in the corpus: inside that file `u8` means
   `uint64_t` while `recon/headers/g1_types.h` says `uint8_t`, so merging `lib/`
   into a TU silently truncates every soft-double helper result to 8 bits. It
   needs one atomic rename plus a `cfg_verify` re-proof. Stage 04's `typedef`
   rule currently refuses the merge, which is why it has not bitten — that is
   containment, not a fix.

7. **The 12 `__`-prefixed compiler-runtime helpers are excluded by rule**
   (`__aeabi_uldivmod`, `__aeabi_ldivmod`, `__aeabi_dadd`, `__divdf3`,
   `__fixdfdi`, `__muldf3`, …). Their prototypes are ABI-fixed and majority vote
   gets them wrong in the silent direction. They need a hand-written table taken
   from the AAPCS run-time ABI document, not from the corpus.

8. **31 symbols were refused as `64bit_return_not_arbitrated`** — some spelling
   claims a 64-bit return, the definition does not assert it, and the image
   cannot refute it because r1 is live at the return via a tail call. Dropping
   the 64-bit half is invisible to the compiler (§2.4), so they are left alone.
   `get_dashboard_sum_time` and `k_sem_take` are in this set.

9. **17 symbols were refused as `canonical_needs_a_nonbase_type`** — the
   canonical would have carried `u32`, `uint`, `byte` or a `struct` tag into
   files that declare none of them. Those need the typedef question settled
   first (Stage 04 §3.0.1: `typedef uint32_t u32` and `typedef unsigned int u32`
   genuinely conflict on this target), which is item 6's problem.

10. **197 files are frozen** — **35** could not be made to compile under any
    canonical (bodies that dereference a parameter the canonical spells as an
    integer: `cjson_delete`, `format_bt_addr_str`, `resource_manger_get`, the
    `atomic_*` builtin wrappers, `kmutex_dlist_init`), and **162** compiled but
    changed their object and were reverted. Each frozen file holds its symbol's entry open. They
    are the reason `assert_post_action` still blocks 29 adjacencies after being
    rewritten in 128 places.

11. **`cfg_verify` was not re-swept, deliberately.** It is structurally blind to
    this defect class — it seeds r0..r3 regardless of the declared arity — so a
    green sweep would be evidence of nothing. Per AGENTS.md and the brief, a
    green `cfg_verify` is never cited here as evidence. The per-object byte
    comparison and the byte-identical flash payload are the evidence.

12. **No new `cfg_verify` fixture was added**, so the "does it fail on a real
    mutation" obligation does not arise.

13. **Nothing was committed.** The tree is left dirty.
